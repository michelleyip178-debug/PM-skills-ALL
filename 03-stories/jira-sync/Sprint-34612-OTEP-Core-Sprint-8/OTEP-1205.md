## Description

A. Provenance recorded on every competency (no API change) AC-A1  — Given an officer's competencies are computed/stored, when the  officer_competency  JSONB is written, then each entry carries a  Sources  array; each source has  Route ,  RefID , and  ImportedAt . AC-A2  — Route values are the business-oriented constants: AGENCY_JOB  (from the job's  core_competency ) —  RefID  = job id WOG_ROLE  (fan-out via  role_competency ) —  RefID  =  role_competency.id  (UUID) OTG_CARRIED_OVER  (carried from  source_otg ) —  RefID  = originating ref SELF_DECLARED  (officer-added) —  RefID  = empty AC-A3  — Given the same competency is reached by more than one route, when entries merge, then all routes are preserved (union by  (Route, RefID) ), deduped, and stably ordered (Route, then RefID). AC-A4  —  ImportedAt  is metadata only: it is  not  part of the dedup key, so re-import of the same  (Route, RefID)  does not create duplicate sources. AC-A5  — No external API contract changes:  Sources  is additive; empty sources serialize as absent ( omitempty ) so existing stored payloads stay byte-identical. B. WOG role reference uses the UUID AC-B1  — Given a fan-out (WOG) competency, when its source is recorded, then  RefID  is the  role_competency.id  UUID (not the  familyCode-functionCode-grade  string), matching the table the UI keys on. AC-B2  — Given  role_competency  upserts on  (role_id) , when a row is updated, then its  id  is preserved ( ON CONFLICT (role_id) DO UPDATE ), so recorded  RefID s stay stable. C. Strict role lookup — the "unrelated competencies" fix AC-C1  — Given a role lookup, when  GetRoleCompetenciesByRefIDs  runs, then it matches strictly on  job_family_id   AND   job_function_id   AND   UPPER(grade label)   AND   is_active , returning only that one role's competencies. AC-C2  — Given grades expressed as  MX* , when canonicalized, then they resolve to the  JR*  equivalent before the label match (e.g.  MX10 → JR10 ). AC-C3  — Given a DB-computed set vs POCDEX's computed set for the same officer, when diffed, then the DB side has  no extra ("unrelated") codes .  Evidence: DB-extra = [] for hannah (48) and aimee (19) on both routes. D. OpsPortal computes the same way as the app AC-D1  — Given the OpsPortal DB snapshot, when it derives expected competencies, then it uses the  same  id-based role lookup ( GetRoleCompetenciesByRefIDs ) as the officer-facing compute — no divergent code path. E. OpsPortal per-user consolidated competencies AC-E1  — Given an eligibility check ( mode:"check" ), when the job completes, then  details.pocdex  and  details.db  each include  consolidated_competencies . AC-E2  — Given an officer with multiple positions (across agencies), when consolidated, then it is  one  per-user list (union of all positions, deduped by  code ), not one list per agency.  Evidence: hannah 6 positions → 48; aimee 2 → 19. AC-E3  — Given a code appears in several positions, when consolidated, then  from_job  /  from_fanout  /  self_added  /  agency_specific  are retained and merged (any-true wins). AC-E4  — Given a side has no competencies, when serialized, then no  consolidated_competencies  key is emitted ( omitempty ). F. Quality gates AC-F1  —  go build ./... ,  go vet ,  gofmt , and all competency + profile + provisioning tests pass in CI. AC-F2  — Admin gating unchanged: provisioning routes remain admin-only (fail-closed  RequireAdmin ).
