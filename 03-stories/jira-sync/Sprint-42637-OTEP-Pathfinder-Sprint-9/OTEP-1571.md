## Description

Context CAM's SCIM 2.0 Connector path identifies privileged users by membership in a group named  "Privileged Group"  (no  isPrivileged  boolean field needed). This group does not currently exist in our Keycloak realm. From  OTEP-1557  (resolved): OTEP has two user tiers -- Administrators ( isPrivileged: true ) and Users ( isPrivileged: false ). Group membership is managed in Keycloak roles/groups, not in the database. What to do Create a Keycloak group named "Privileged Group"  in the  otep  realm Create a corresponding Keycloak role  (e.g.,  privileged ) if role-based access control is needed alongside group membership Add existing admin users  to the "Privileged Group" Update realm config  ( realm-config/ ) so the group is provisioned consistently across environments via keycloak-config-cli Acceptance criteria "Privileged Group" exists in the  otep  realm in all environments Admin users are members of "Privileged Group" Non-admin users are NOT members of "Privileged Group" Group is visible via Keycloak Admin Console and SCIM Groups endpoint ( GET /realms/otep/scim/v2/Groups ) Realm config JSON is updated so the group is created automatically on deployment Notes This replaces the  ADMIN_EMAILS  env var approach (decided in  OTEP-1557 ) If  OTEP-1563  (Connector path) is confirmed, CAM will read this group to determine privileged users If  OTEP-1563  is not confirmed (fall back to Agent API path), the custom SCIM handler would map this group membership to  isPrivileged: true  in the CAM extension schema -- so the group is needed either way

## Latest Comments

**Hao Eng** (2026-09-14)
Update: switched from realm role to client role Changed the  admin  role from a  realm role  to a  client role on `otep-client` . Why Realm roles are global across all clients. If another client (e.g.,  dle-client ) later needs its own  admin  role with different semantics, a realm role would conflict. Client roles scope the  admin  permission to  otep-client  only, keeping each client's authorization independent. What changed Before After prd/10-roles.json  — realm role prd/71-roles.json  — client role on  otep-client prd/20-groups.json  —  realmRoles: ["admin"] prd/72-groups.json  —  clientRoles: { "otep-client": ["admin"] } Role files numbered  10-  (before clients) Role files numbered  71-  (after  70-clients.json , since client must exist first) JWT impact The  admin  role now appears under  resource_access.otep-client.roles  instead of  realm_access.roles : {
  "resource_access": {
    "otep-client": {
      "roles": ["admin"]
    }
  }
} The app needs to read from this path when checking admin access. File ordering Files are renamed to respect keycloak-config-cli's alphabetical processing order: 70-clients.json  → client created 71-roles.json  → client role defined (requires client to exist) 72-groups.json  → role mapped to group (requires role to exist) 90-users/  → users assigned to group
