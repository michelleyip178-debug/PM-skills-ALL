## Description

Problem Summary During the 15-minute 100-VU distributed frontend performance test on UAT (18:02–18:18 SGT), the frontend cluster encountered  1,022 SSR crashes .  440 of these crashes (43.1%) occurred directly on the  /opportunities  route , making it the single most impacted endpoint across the entire application. Performance Test Impact SSR Crashes : 440 crashes on  /opportunities  out of 1,022 total across  otep-web . Pass Rate Degradation : Overall check pass rate plummeted to  29.62%  due to failed HTML streaming and error boundary fallbacks. CPU Spike : Node.js server processes pegged CPU utilization at  97.72% . Autoscale Storm & Subnet Exhaustion : CloudWatch Alarm  TargetTracking-service/ecs-psd-otep-uat-app/otep-web-CPUUtilization-High  scaled  otep-web  from 2 to 20 tasks, which completely exhausted all available private IP addresses in  subnet-0809cd873a0437e67  and  subnet-0f8c9bf8b99a5705e  ( InsufficientFreeAddressesInSubnet ). Root Cause Analysis Culprit Component :  src/components/ui/PageLoadingSpinner.tsx  directly renders  LoadingDotsSpinner  from  @lifesg/react-design-system  (v3.5.0-canary.5). SSR Evaluation : Even though marked  "use client" , Next.js 16 App Router pre-renders Client Components on the server during initial SSR streaming. Lottie Evaluation on Node : Inside  @lifesg/react-design-system ,  LoadingDotsSpinner  uses  React.lazy(() => import("./lottie-animation.js")) . When evaluated by Node.js on the server, the bundled  lottie-web  module executes top-level browser code ( createTag  calling  document.createElement("canvas") ). Uncaught Exception : Because  document  does not exist in the Node runtime, it throws an unhandled: ReferenceError: document is not defined
    at createTag (/@lifesg/react-design-system:1:571)
    at requireLottie (/@lifesg/react-design-system:1:304042)
    at module evaluation (/@lifesg/react-design-system:1:312922)
    at module evaluation (/app/.next/server/chunks/ssr/17ym_react-design-system_animations_loading-dots-spinner_lottie-animation_18fmka0.js:1:10849) Why /opportunities was the hardest hit Missing Route-Level  loading.tsx : Unlike  /learningcourses ,  /opportunities  lacks a localized  loading.tsx  boundary. When suspended, Next.js falls back to the root  src/app/loading.tsx , which renders  PageLoadingSpinner . Sequential Async Waterfall in  OpportunitiesPage : OpportunitiesPage  awaits  getCategories() , immediately suspending the route and triggering  PageLoadingSpinner . Concurrently,  RootLayout  awaits  getUserProfile()  behind  <Suspense fallback={<AppBodyFallback />}> , which also renders  PageLoadingSpinner . OpportunityListLoader  then awaits  getOpportunities({ ...searchParams }) , prolonging the suspended state. Traffic Amplification : In the k6 opportunities journey (22% VU share), 100% of requests hit  /opportunities  with  page=1  and query parameters. Because  searchParams  are dynamic, Next.js cannot statically cache the page, forcing dynamic SSR on every hit. Why CI/Dev Missed It Vitest : Runs in  jsdom  (where  document  is mocked) and all unit tests in  __tests__  mock  @lifesg/react-design-system  with  vi.mock() . pnpm build : Pages using dynamic  searchParams  are marked as dynamic (ƒ) and skipped during build-time static generation. Proposed Remediation Route-Level Defensive Isolation (Path Finder Squad) : Add  src/app/opportunities/loading.tsx  rendering pure CSS skeletons ( OpportunityListSkeleton.tsx ) rather than inheriting the root spinner. Parallelize  getCategories()  and  getOpportunities()  with  Promise.all()  to remove waterfall delays. Global Frontend Fix : Update  src/components/ui/PageLoadingSpinner.tsx  to use  next/dynamic  with  ssr: false  and a CSS spinner fallback, preventing  LoadingDotsSpinner  from ever evaluating on Node.
