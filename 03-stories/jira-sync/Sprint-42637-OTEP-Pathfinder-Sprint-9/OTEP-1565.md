# OTEP-1565: Enforce bounded capacity on in-memory LRU caches (authorizer & user resolver)

## Description

Tagging for visibility and triage:   . 1. Issue Summary Two in-memory LRU caches in  otep-service  are initialized with  size = 0 :
 1.  internal/shared/auth/authorizer.go:25  (CachedPOCDEXClient)
 2.  internal/shared/user/resolver.go:76  (CachedIDResolver)
 In  hashicorp/golang-lru/v2/expirable , passing  size: 0  turns off the LRU eviction policy entirely, leaving the caches unbounded and vulnerable to memory expansion. 2. Affected Code Locations In  internal/shared/auth/authorizer.go:24-27 : func NewCachedPOCDEXClient(client POCDEXClient) *CachedPOCDEXClient {
    cache := expirable.NewLRU[string, struct{}](0, nil, 10*time.Minute) // LRU disabled
    return &CachedPOCDEXClient{client: client, cache: cache}
} In  internal/shared/user/resolver.go:75-78 : func NewCachedIDResolver(resolver IDResolver) *CachedIDResolver {
    cache := expirable.NewLRU[string, uuid.UUID](0, nil, 10*time.Minute) // LRU disabled
    return &CachedIDResolver{resolver: resolver, cache: cache}
} 3. How It Was Analysed Static Code Analysis:  A static audit of in-memory caching and state retention across the repository searched for cache initializations (expirable.NewLRU). Both caches were found to pass 0 as the first argument. Vendor Contract Verification:  Inspecting hashicorp/golang-lru/v2/expirable source code confirmed: "Size parameter set to 0 makes cache of unlimited size, e.g. turns LRU mechanism off." Git Archaeology:  Tracing git history (git log -S "expirable.NewLRU") revealed the pattern was first introduced in internal/shared/auth/authorizer.go (commit 3756b91c, OTEP-190) and subsequently replicated in internal/shared/user/resolver.go (commit 369c283a, OTEP-390). 4. Risk & Failure Modes Uncapped Memory Retention:  While entries expire after a 10-minute TTL, there is no upper ceiling on capacity. Under high traffic volume or distinct email lookups, entries accumulate without bound inside that 10-minute window. Resource Starvation:  Under memory pressure against the ECS container memory limits (1 GB / 2 GB), an unbounded map can cause memory spikes and contribute to OOM events. 5. Recommended Fix Enforce an explicit maximum capacity limit (e.g.  10,000  entries) on both caches to re-enable LRU eviction while preserving the 10-minute TTL: // internal/shared/auth/authorizer.go
cache := expirable.NewLRU[string, struct{}](10000, nil, 10*time.Minute)

// internal/shared/user/resolver.go
cache := expirable.NewLRU[string, uuid.UUID](10000, nil, 10*time.Minute)
