# OTEP-1564: Close HTTP response body on non-200 status in CFT client to prevent socket/connection leak

## Description

Tagging for visibility and triage:      . 1. Issue Summary In  internal/shared/cft/client.go:135-145 , when  c.httpClient.Do(req)  succeeds but the upstream CFT API returns a non-200 HTTP status (e.g., 401, 403, 404, 500, 502), the method returns immediately without closing  resp.Body . This causes an unclosed socket, file descriptor, and TCP connection pool leak. 2. Code Snippet func (c *HTTPClient) Download(ctx context.Context, workflowID, fileID string) (io.ReadCloser, error) {
    ...
    resp, err := c.httpClient.Do(req)
    if err != nil {
        return nil, fmt.Errorf("download request: %w", err)
    }

    if resp.StatusCode != http.StatusOK {
        // BUG: resp.Body is never closed on non-200 status code!
        return nil, fmt.Errorf("api error (status %d)", resp.StatusCode)
    }

    return resp.Body, nil
} 3. How It Was Detected via Static Analysis During a forensic memory and resource audit across the repository, control-flow branch analysis was conducted on all HTTP client execution points ( .Do() ) to verify that  resp.Body.Close()  executes across every branch: Happy Path (200 OK):  In internal/shared/cft/handler.go (lines 116–120), the caller receives resp.Body as fileReader and properly defers fileReader.Close(). Under normal successful downloads, no leak occurs. Error Path (Non-200):  When resp.StatusCode != http.StatusOK, client.go returns directly with fmt.Errorf(...) without returning resp.Body to the handler. Because resp.Body is neither closed inside Download() nor passed to the caller, the response body and its underlying network connection are orphaned. 4. Risk & Failure Modes (Why It Is Critical) TCP Connection Pool Exhaustion:  Go’s http.Transport only returns persistent TCP connections to the idle pool when resp.Body is fully read and closed. Unclosed bodies leave connections marked permanently in-use, quickly exhausting MaxConnsPerHost/MaxIdleConns and causing subsequent CFT calls to hang until timeout. Linux File Descriptor (FD) Exhaustion:  Every leaked socket holds an open file descriptor against the container limit (ulimit -n). Once reached, the container fails globally with "accept: too many open files", breaking ALB health checks and triggering ECS container restarts. Kernel Memory Leak:  Each open TCP socket maintains kernel receive/send buffers (128 KB–512 KB) that cannot be freed by Go GC. Cascading Outage Risk:  The leak triggers precisely when upstream CFT has an issue (e.g. rate-limiting, expired credentials, or 502/504 gateways). Retrying failed downloads rapidly burns all available sockets, taking down the otep-service container. 5. Recommended Fix Add an explicit  _ = resp.Body.Close()  before returning on non-200 status:     if resp.StatusCode != http.StatusOK {
        _ = resp.Body.Close()
        return nil, fmt.Errorf("api error (status %d)", resp.StatusCode)
    }
