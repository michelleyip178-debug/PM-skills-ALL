## Description

Context Same parent doc as  otep-service  . ABLR needs identity/authentication events from Keycloak — logins, logouts, token exchanges, impersonation, federated logins, and admin actions (realm config changes, user/client CRUD via the admin console). This is separate from otep-service's business-action audit trail — Keycloak has its own native, built-in event-logging system, so this ticket is config-only, no application code. Verified against the real otep-keycloak repo Realm config is managed via a base + overlay pattern: realm-config/base/ .json (shared across all envs) + realm-config/<env>/ .json (per-env additions/overrides), merged at Docker build time into /config/<env>/, then applied via keycloak-config-cli's IMPORT_FILES_LOCATIONS env var at runtime. No Dockerfile or pipeline changes needed for this ticket — confirmed against the actual repo, not just the design doc. Files are processed sequentially in filename order within a merged directory. Different filenames targeting the same underlying realm resource are fine and expected — 00-realm-base.json already sets base realm fields (displayName, loginTheme, etc.) separately from 30-authentication-flows.json; a new 05-events.json fits this same established pattern for events-specific settings.  The 9-field audit format Every audit line is a single pipe-delimited string with fields in this exact order: * Field Description Where it comes from in OTEP 1 Timestamp dd-mm-yyyy hh:mm:ss  Server time at emit 2 Action  CREATE, UPDATE, DELETE, LOGIN, UPLOAD, IMPORT, etc  Derived from HTTP method for generic cases; explicitly set for the named P1 events below 3 Object The resource/entity acted on (e.g. Profile, Provisioning:BulkJob)  Route path (generic) or explicit string (named events) 4  Action By  Who performed the action Keycloak preferred_username or subject UUID from the JWT — never email or NRIC 5  Admin Group Privilege level  admin or user, derived from JWT role claims 6 Role User's role label Officer or Administrator, derived from JWT role claims 7  Project Reference  Correlation ID  X-Request-ID header (check if this already exists elsewhere in the request pipeline before adding new plumbing) 8  Event Description  Human-readable detail of what happened  Contextual, written per call site 9  Server Hostname  Which container handled it ECS task hostname (likely just the HOSTNAME env var) Example line:  10-09-2026 14:30:00|CREATE|Profile|john.doe|user|Officer|req-abc-123|Officer profile resolved via POCDEX|ip-10-0-1-45.ap-southeast-1.compute.internal Proposed Change(Open to team discussion if got better solution) Enable the events subsystem events.json: {
"realm": "otep",
"eventsEnabled": true,
"adminEventsEnabled": true,
"adminEventsDetailsEnabled": true,
"eventsExpiration": 7776000
} Option 1 — Custom Keycloak Event Listener SPI (Java) Write a Java plugin implementing Keycloak's EventListenerProvider interface (onEvent(Event) for user events, onEvent(AdminEvent, boolean) for admin events — verified against Keycloak's own API docs), which builds and writes the pipe-delimited line directly, replacing the native jboss-logging listener. Deployment: package as a JAR, drop into otep-keycloak/providers/ (existing empty slot, already wired into the Dockerfile's COPY providers/ /opt/keycloak/providers/ + kc.sh build step — no new build mechanism needed) Config events.json sets eventsListeners to the custom provider's ID instead of jboss-logging Pros : transformation happens at the true source; most direct mapping from Keycloak's rich event objects to the target fields Cons : requires Java/Keycloak-SPI development — a different skillset than this team's primary stack (Go/Terraform); need to track Keycloak's SPI interface across version upgrades (pinned at 26.6.1 today) Option 2 — FireLens/Fluent Bit transform at the ECS layer Add a  Fluent Bit sidecar  container to the  otep-auth  ECS task (AWS's native awsfirelens log driver). Keycloak keeps emitting its native format unchanged; the sidecar intercepts it in transit and reshapes it via a Lua filter before it reaches CloudWatch. Mechanism: main container's logDriver switches from  awslogs  to  awsfirelens ; sidecar has firelensConfiguration: {"type": "fluentbit"}; a Lua filter parses Keycloak's type="LOGIN", ... string and rebuilds it as the 9-field pipe line; cloudwatch_logs output plugin writes the transformed line to the same /ecs/prd/otep-auth log group.  Deployment: custom sidecar image (extends AWS's public.ecr.aws/aws-observability/aws-for-fluent-bit:3 base, config + Lua script baked in — confirmed Fargate does not support S3-hosted config, only baked-in file type), new ECR repo, same pattern as every other container in this stack Pros : stays entirely within otep-iac's existing ownership and tooling (Dockerfile/ECR/Terraform); no Java/Keycloak-internals expertise needed; Keycloak itself is untouched Cons : extra sidecar container (small additional CPU/memory in the Fargate task); Lua string-parsing is less flexible than real code if Keycloak's event data gets complicated; one more moving part in the ECS task definition Acceptance Criteria [ ] events.json merges correctly created for prd [ ] LOGIN/LOGOUT/IMPERSONATE events visible in /ecs/prd/otep-auth CloudWatch log group after deploy [ ] Admin events (realm config, client/user CRUD) captured References Parent doc: "OTEP — ABLR Splunk SIEM Integration Plan"
