**Thomas Huchedé** (2026-05-22)
URL Query Parameters for Pre-fill To pre-fill user data dynamically from OTEP into FormSG, we must construct custom query links targeting the specific cryptographic field IDs generated by FormSG. URL Structure:  https://form.gov.sg/ <form_id>?<field_id_1>=<value_1>&<field_id_2>=<value_2> Parameter Requirements: Keys: Must be the specific alphanumeric question hashes generated by FormSG (e.g., 64bf87a90b...), not plain-text field names like email or name. Values: Values pulled from OTEP must be strictly URL-encoded (e.g., spaces converted to %20 or +, @ symbols to %40). Example Integration Link:  https://form.gov.sg/654ab1234?64bf87a90b11=John+Doe&64bf87b90b22=john%40example.com Webhook Payload Schema & Authentication Mechanism FormSG operates in an end-to-end encrypted Storage Mode. Webhooks endpoint in OTEP must first verify the signature before processing the payload. Every webhook event includes an  X-FormSG-Signature  header Header Format:  t=<epoch_timestamp>,s=<submission_id>,f=<form_id>,v1=<signature_hash> Verification: we must use this header, the public incoming request URI, and the Webhook Secret Key to check if the signature matches the payload cryptographic hash Raw Webhook Payload: the raw POST body contains an encrypted package block. We cannot read the form answers directly from this block without the form's private  .txt  secret key {
   "data": {
       "formId": "654ab1234",
       "submissionId": "sub_890xyz...",
       "encryptedContent": "h7G2+bK...[Long Base64 Encrypted String Containing Responses]...",
       "version": "1.0.0"
   }
} Decrypted Payload Schema: a JSON array of objects representing user responses [
   {
       "_id": "64bf87a90b11",
       "question": "Full Name",
       "answer": "John Doe",
       "fieldType": "short-text"
   },
   {
       "_id": "64bf87b90b22",
       "question": "What is your primary email address?",
       "answer": "john@example.com",
       "fieldType": "email"
   }
] Potential Security Concerns & Loopholes PII Leaks via Pre-fill URLs Because pre-fill data is passed strictly via URL query parameters, it is exposed in cleartext across browser histories, client-side extensions, and proxy server logs. We should  NOT  pass highly confidential data (e.g., medical info, passwords, unauthenticated NRICs) using pre-fill. If verified identity is required, we should consider using the native Singpass/MyInfo integrations. Signature Replay Attacks  If we verify the signature hash but fails to inspect the timestamp (t=) or track unique submissionId values, an attacker could intercept a valid payload and re-post it to OTEP multiple times. Compromised/Lost Secret Keys The form  .txt  key is generated only once to the admin's local machine upon creation. FormSG cannot recover lost keys. OTEP must treat the uploaded  .txt  form secret key as a critical app secret, storing it securely in a specialized credentials vault. Additional Notes No APIs: We cannot programmatically provision or update forms from OTEP via code or REST endpoints. Setting up new forms will always require an administrator to manually build the form inside the FormSG interface, download the keys, link the webhook, and create a mapping between the fields  id s and the user's data for pre-filling. Mapping Layer for pre-filling: Because FormSG assigns random strings as  _id  keys, we must maintain a mapping to be able to pre-fill values (name, email,...). Edition: If an operational admin deletes a question on FormSG and re-creates it with the exact same visual wording, FormSG assigns a brand new alphanumeric  _id . This immediately breaks both the pre-filling and the webhook parser until the mapping are manually updated. Conclusion Pre-filling is possible but requires a lot a manual configuration each time a form is created The webhook need to be configured manually by the person creating the form For existing form this means that we need to edit the form and register both the webhook secret key in OTEP and the original form private  .txt  secret key
