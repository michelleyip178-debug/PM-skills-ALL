**Soumya Routa** (2026-05-11)
Current IAC code spec summary details:  1. Core Architectural Strategy The OTEP platform is a secure, government-compliant infrastructure designed for the  Public Service Division (PSD) . It follows a  "No hand-provisioning"  philosophy, utilizing Terraform and Terragrunt to ensure all resources are code-defined and reproducible. Two-VPC Topology The platform implements a strict  two-VPC segmentation model  to isolate public-facing entry points from private application logic: Internet VPC ( 100.108.253.0/24 ) : Houses public-facing components like the  reverse-proxy ,  singpass-proxy , and the Internet ALB. Intranet VPC ( 10.188.186.128/25  &  100.100.238.128/25 ) : Contains core application services ( service-a ,  service-b ), internal ALBs, and Aurora PostgreSQL databases. VPC Peering : A module-managed peering connection facilitates private communication between the Internet  proxy_private  subnets and the Intranet  internal_alb / app_private  subnets. 2. Networking & Traffic Inspection The platform enforces Singapore Government IM8-compliant network segmentation through symmetric and asymmetric inspection paths. AWS Network Firewall (NFW) Implementation Internet VPC (Symmetric) : All ingress (via IGW Edge Route Table) and egress traffic must pass through an NFW endpoint tier for inspection. Intranet VPC (Asymmetric) : Egress traffic to corporate networks (WOG) via the Transit Gateway (TGW) is inspected. However, TGW ingress traffic arrives directly at workloads to allow for external management of return traffic. Threat Blocking : NFW rule groups consume blocked IP and domain lists from JSON files; large IP lists are automatically chunked into groups of 500. IP Allocation & Routing RFC6598 Usage : To avoid conflicts with the massive WOG  10.x.x.x  address space, application workloads use the  100.x.x.x  CGNAT range. Transit Gateway : Connectivity is restricted to specific CIDRs; the platform strictly forbids a default route ( 0.0.0.0/0 ) via TGW. 3. Infrastructure as Code (IaC) Framework The platform is built on a modern toolchain designed for "contract-first" validation. Tooling : Terraform  >= 1.5.0  and Terragrunt  1.0.3 . State Management : State is stored in S3 (pattern:  sst-s3-psd-otep-{env}-tfstate ) with native S3 locking enabled. Configuration Hierarchy : A layered model ( common.hcl  →  account.hcl  →  root.hcl ) ensures that global settings, such as provider-level tags and blocklists, are applied consistently across all environments. 4. ECS Compute & Load Balancing The compute layer is divided into specialized modules to maintain a DRY (Don't Repeat Yourself) codebase. Key Modules shared : Creates IAM Task Execution Roles and CloudWatch Log Groups. It only grants Secrets Manager access if specific ARNs are provided. cluster : Provisions ECS Fargate clusters utilizing both standard  FARGATE  and  FARGATE_SPOT  capacity providers. internet-service  vs  intranet-service : Internet Services : Located in the Internet VPC, these services can egress to the internet (via NFW+NAT) and to the Intranet VPC (via Peering). Intranet Services : Isolated from the internet, these listen to internal ALBs and allow ingress from the  reverse-proxy . Load Balancing Logic Internet ALB : Publicly accessible; it automatically redirects HTTP to HTTPS if an ACM certificate ARN is provided. Internal ALB : Private to the Intranet VPC; used for routing traffic between the proxy layer and backend workloads. 5. Security & Compliance Baseline Interface Endpoints : A baseline of 6 services (ECR API, ECR Docker, CloudWatch Logs, Secrets Manager, KMS, SSM) is enforced in the Intranet VPC to keep management traffic off the public internet. Gateway Endpoints : S3 and DynamoDB gateway endpoints are attached to all  app_private  route tables. IAM Least Privilege : Task roles are scoped strictly to required resources like ECR and specific secrets. Tag Governance : Mandatory tags (Org, Project, Environment, etc.) are applied to every resource via provider-level  default_tags . 6. Implementation Roadmap The project is currently in  Phase 3 : Phases 1 & 2 (Complete) : Established the networking contract schema and provisioned real resources like VPCs, NFW, and TGW routes. Phase 3 (In Progress) : Focuses on ECS module scaffolding and Terragrunt wiring. Phases 4–6 (Planned) : Will include RDS/Aurora deployment, Route 53/ACM management, and live container deployments.
