# OTEP-601: admin feature to bulk-provision officer accounts.

**Type:** Story
**Status:** Backlog
**Assignee:** N/A
**Story Points:** N/A

---

## Description

Add an  admin feature to bulk-provision officer accounts . In production, an admin supplies officer emails; the system resolves each via  POCDEX , creates the account, and loads role + OTG competencies. In non-production, the same screen instead accepts a  JSON payload to seed test users  (POCDEX is mocked in dev). Provisioning runs  asynchronously , with  per-email status + logging  persisted to a new audit table. Background / Context The full create-and-load engine  already exists :  POST /api/v1/profiles/identity  ( profile.ResolveIdentity(email) ) resolves an email via POCDEX →  GetOfficer  → employments → position →  upserts  officer / employment / position_jobinfo  →  BuildAndUpsertOfficerCompetencies  (role + OTG). Today it only reads the email from the  caller's own JWT , so an admin cannot provision  other  users, and there is no bulk or audit capability. This story exposes that engine to admins for many emails, with tracking. Goal (user story) As an  OTEP admin,  I want to  provision multiple officer accounts at once from a list of emails (prod) or a JSON seed (dev),  so that  users are preloaded with their profile and competencies before first login, and I can see which succeeded/failed. Scope In scope otep-web admin page  /my-admin/provision  (behind the existing  ADMIN_EMAILS  gate), with  environment-gated input : Production  → comma-separated  emails  textarea. Non-production  →  JSON  textarea + a  "Download sample JSON"  button (client-side template download). otep-service: new admin endpoints,  async  processing, and a  persisted per-email audit trail . Per-email result + structured logging; one failure must not abort the batch. Dev-only JSON seed path that reuses the existing officer/competency mapping,  hard-gated to non-prod . Out of scope Keycloak user creation / role assignment / notifications / activation links. CSV or file-upload ingestion (paste only). Approval workflow / scheduling. Re-sync on role change. Solution overview Production — email flow (per email, reusing  ResolveIdentity ) Resolve email → POCDEX UID Fetch + validate officer from POCDEX Up-to-date check Active employments → position(s) + resolve  agency/job_grade/job_family/job_function Upsert  officer  +  employment  +  position_jobinfo Load  role  +  OTG  competencies Non-production — JSON seed flow (dev only) Admin pastes an array of user objects (officer + employments → position; competencies are  derived , not listed). Seed path maps the JSON to the same domain structs and runs the existing upsert + competency steps,  bypassing POCDEX . Sample template downloadable from the UI. Technical design otep-service Migration  —  account_provisioning_job  (id, requested_by, total/success/failed counts, status  processing|completed|completed_with_errors , timestamps) +  account_provisioning_item  (id, job_id FK, email, status  pending|success|failed , profile_id, error_message, timestamps). POST /api/v1/admin/profiles/provision  — body  { emails: "a@x,b@y" } ; returns  202   { job_id, total } ; captures caller email as  requested_by . Auth: existing  RequireAuthN  (admin authorization enforced in otep-web's  /my-admin  gate). GET /api/v1/admin/profiles/provision/{job_id}  — job summary + per-email items (for UI polling). Async worker (in-process, Option A)  — bounded goroutine pool on a  detached context ; per email calls  ResolveIdentity ; updates the item (success+ profile_id  / failed+reason) and logs; updates job counts/status on completion.  Startup sweep  re-processes  pending  items after a restart. Dev-only seed handler  — gated on  APP_ENV / IS_LOCAL ; maps the JSON → existing upsert + competency path. otep-web /my-admin/provision  page (mirrors the existing Issues admin feature), env value passed server-side to choose the input mode. apiFetch  helpers:  provisionAccounts()  → POST;  getProvisionJob()  → GET (polled). Results table:  email │ status │ profile / error , auto-refreshing until the job completes. "Download sample JSON" button (Blob download, valid JSON template). Acceptance criteria Admin (in  ADMIN_EMAILS ) can open  /my-admin/provision ; non-admins are redirected. Prod : pasting N comma-separated emails creates a job, returns immediately, and provisions asynchronously. Each email's outcome (success + profile id, or failed + reason) is persisted and visible in the results view. A single failing/invalid email does  not  stop the others; job ends  completed_with_errors . Successful emails have an  officer  +  employment  +  position_jobinfo  and  role + OTG competencies  loaded. Non-prod : the screen shows the JSON input + a working  Download sample JSON ; pasted JSON seeds users; this path is  unavailable in production . Raw emails are  not  written to application logs (PII); logs key on job_id/profile_id. After a service restart mid-job,  pending  items resume. go build / go test  and otep-web  tsc /lint/tests green; OpenSpec change added. Preconditions / dependencies Reference data seeded ( ref_agency ,  ref_job_grade ,  ref_job_family ,  ref_job_function ) and  role_competency  populated. OTG staging ( source_otg_officer_competency ) populated for OTG competencies to load. POCDEX reachable (prod) / mock running (dev).
